# 첫집 내비 서비스 소개 v4 기준 변경사항 정리

풀스택 팀 문서(PRD v1.0, 프로젝트 명세서 v1.0, DB 스키마 v0.1, 모두 2026-11-14 작성)와 **서비스 소개 v4**(2026-11-16, 본선 2026-11-21 기준)를 비교한 문서예요. 풀스택 문서를 v4에 맞추려면 무엇을 지우고, 고치고, 더해야 하는지 정리했어요.

> **한 줄 요약**
> 4단계 → **3단계**(내 상황 → 지원 추천 → 집 비교). 주거 전략 단계와 카카오모빌리티 자동차 길찾기는 **빠졌어요**. 공고문 RAG 상담, 조건 변경 재계산, 집별 지원 판정, 대중교통(ODsay), 매물 정보 자동 입력, AI 추천 보조, 시각장애 청년용 음성 모드가 **들어왔어요**. 한 달 실부담(월세 + 관리비)과 점수 가중합 방식은 **풀스택 문서와 같아요**.

## 2. 없어진 것

### 2.1 주거 전략 단계 전체

v1.0의 STEP 2는 전세·월세 전략의 초기 필요자금과 월 부담을 비교했어요. v4에는 이 단계가 없어요.

**왜 뺐나**

- **사용자는 이미 매물을 정한 상태로 들어와요.** 첫집 내비는 직방·다방 등에서 본 후보 집을 들고 와서 "어디로 갈지" 고르는 서비스예요. 주거 전략은 매물이 없는 상태에서 "이런 집이면 이렇다"는 가상의 매물을 기준으로 추천하는 구조라 흐름이 맞지 않아요.
- **실제 매물을 가져올 수 없어요.** 직방·다방·네이버부동산은 공개 API가 없고, 크롤링은 이용약관 위반이에요. 그래서 전략 단계에서 쓸 수 있는 건 가상의 금액뿐이에요.
- **비용 비교는 3단계에서 해요.** 사용자가 넣은 실제 후보 집의 보증금·월세·관리비로 한 달 실부담과 집별 지원을 계산하니까, 전략 단계가 하던 역할을 실제 금액으로 대신해요.

**빠진 기능**

| 기능 | 원래 하던 일 |
|---|---|
| 전세·월세(·청년주택) 전략 카드 | 초기 필요자금과 예상 월 부담 비교, 적용 금리·산정 기준 표시 |
| 대출 이자 계산 | 버팀목·보증부월세 대출의 한도·금리를 적용한 월 이자 (보증부월세 구간 금리 포함) |
| 청년주택 전략 | SH 청년안심주택 임대료로 비용 예시 |
| 2년 살아보기 (데이터·AI 쪽 초기안) | 전략별 월별 비용과 2년 총비용 |

풀스택 문서에서 같이 빠지는 곳:
- PRD R2, 1절 성공 기준의 "비용 가정이 표시된 전략 2개 이상 비교"
- 명세서 `POST /api/strategies/evaluate`, 5절 전략 비교 계산식, 6절 "전략 비교" 검증 항목, 6인 분담의 "전략" 담당
- DB `loan_product_versions`의 계산용 구조, 확장 테이블 `sh_housing_units`("SH 전략")

**빠진 데이터**

| 데이터 | 전략 단계에서 쓰던 곳 | v4 |
|---|---|---|
| 서울 전월세 실거래 (데이터·AI 쪽 초기안) | 동네별 원룸 시세 중앙값 → 전략 비용의 기준 가격 | **빠짐**. "예산에 맞는 동네" 추천으로 다음 단계에만 남음 |
| 전월세 전환율 (데이터·AI 쪽 초기안) | 보증금 ↔ 월세 환산 | **빠짐**. 정책 판정에 쓰는 보증금 환산율은 공고에 정해진 고정값이라 이 데이터와 별개 |

### 2.2 카카오모빌리티 자동차 길찾기

PRD 머리말에 "확정 사항"으로 적혀 있었고, 명세서 4절 전체가 이 API 기준이에요. v4는 **ODsay 대중교통**을 써요.

- 같이 바뀌는 것: 명세서 `RouteResult.mode=car`, `GET /v1/directions` 흐름, "멀티캠퍼스 역삼까지 자동차로 약 25분" 문구 예시, "택시비·통행료 제외" 안
- 청년 1인 가구는 대부분 대중교통으로 출퇴근하니까 서비스 대상에 더 맞아요.

### 2.3 v1.0 프로필 일부 필드

v4의 9개 질문에는 다음 항목이 없어요.

- 자산(`asset_won`), 연소득(`annual_income_won`): 월소득(세전)만 받아요.
- 주민등록 지역(`registered_region`), 희망 자치구·동(`preferred_gu`, `preferred_dong`)
- 보증금 예산·월세 예산(`deposit_budget_won`, `monthly_rent_budget_won`): v4는 "모아둔 돈"만 받고, 월세 상한 대신 집 비교에서 실부담으로 봐요.

## 3. 바뀐 것 (단계별)

### 3.1 1단계 · 내 상황

| | v1.0 | v4 |
|---|---|---|
| 방식 | 상황을 자연어로 한 번에 입력 → 추출 → 확인. 빠진 무주택·세대 조건만 추가 질문 | 챗봇이 **9가지를 하나씩** 물음. 버튼을 누르거나 말하듯 입력 |
| 질문 항목 | 나이, 거주지역, 소득, 자산, 가용 현금, 입주계획, 무주택, 세대, 자주 가는 곳 | **나이, 상황(직장인·학생 등), 회사·학교, 보증금(모아둔 돈), 소득, 출퇴근 허용 시간, 입주 시기, 집 유무, 세대 분리** |
| 목적지 | "자주 방문하는 곳" 이름+주소 1개 | 회사·학교. 넓은 지명은 다시 물음("강남" → 강남역·역삼역·선릉역·멀티캠퍼스 역삼 중 선택) |
| 입력 정규화 | 언급 없음 | "회사 다녀요" → 직장인, "1억 5천" → 15,000만 원, "한시간 반" → 90분 |
| 오입력 | 추출 실패 시 재시도·수동 입력 | "직", "ㅁㄴ", 한/영 오타(rkdsk)는 넘어가지 않고 다시 물음 |
| 확인·수정 | 프로필 확인 화면 | 9개 답 **정리 카드**, 카드를 누르면 그 질문만 다시 물음 |
| 끝난 뒤 대화 | 없음 | 질문("35살인데 받을 수 있어요?")은 공고문 근거로 답하고 **조건은 그대로**. 말로 알린 변화("월급 250으로 올랐어요")는 **조건을 바꿈** |

### 3.2 2단계 · 지원 추천

| | v1.0 | v4 |
|---|---|---|
| 정책 수 | 구조화 정책 5~10개 목표 (현재 4개) | 금액 계산 3개(국토부 청년월세, 서울시 청년월세, 중개보수·이사비) + **더 찾아본 지원** 5개(안심계약 도움서비스, 청년안심주택, 전월세 대출보증, 임차보증금 이자지원, 주거공유) |
| 결과 표시 | 정책별 조건 충족 여부와 모집 상태를 따로 표시 | **"최대 520만 원"처럼 총액** + 지금 신청 가능 / 내년 신청 지원으로 나눔 |
| 중복 수혜 | 알려진 중복 금지를 경고로 표시 (최적화는 P2) | 국토부·서울시 중복 불가 시 **금액 큰 쪽 자동 선택** |
| 소득 기준 | 중위소득 데이터·기준일 확인 필요 | 2026년 1인 기준 중위소득 월 256.4만 원(보건복지부 고시). 세전 월급으로 추정, 실제 심사는 서류 |
| 월세 조건 | 월세 초과 시 보증금 환산 예외는 REVIEW로 둘 수 있음 | **코드로 계산**: 보증금 × 5% ÷ 12 + 월세 ≤ 93만 원 |
| 조건 변경 | P1 | 핵심 기능. 27세 520만 → 35세 280만, 41세·집 있음 → 지원 없음+이유, 월 420만 → 480만 |
| 일정 | 회차별 모집 상태 | 시연일 기준 올해 접수 종료 여부 판정 + 내년 공고 알림 표시 |

### 3.3 공고문에 물어보기 (RAG)

v1.0에서는 P1(R7)이었고 DB의 `rag_chunks`는 "확장 시 추가할 테이블"이었어요. v4에서는 2단계 핵심 기능이에요.

- 데이터: 온통청년·정부24·주택도시기금·SH 공고문 약 1,200개 조각, TF-IDF 검색
- 답 아래 근거 원문과 "원문 보기" 링크를 붙여요.
- 근거가 없으면 "찾지 못했어요" + 상담기관 안내. 만 19~39세 밖 질문은 AI 없이 복지로(129)·120으로 안내해요.
- 평가: 공고문 원문과 대조한 22문항. 검색 22/22, 근거 20/20, 답 22/22 (LLM 연결 전 14/22)
- 평가 중 찾은 오류(예외 조항 누락, 근거 없는 "안 돼요", 정책 이름 혼동)는 코드 판정과 검사 장치를 더해서 고쳤어요.
- 서버가 꺼져 있으면 미리 준비한 답으로 바꿔서 화면이 깨지지 않아요.

### 3.4 3단계 · 집 비교

| | v1.0 | v4 |
|---|---|---|
| 매물 입력 | 주소와 보증금·월세·관리비를 직접 입력 | 직접 입력 또는 **매물 정보 자동 입력** (4.3 참고) |
| 출퇴근 | 카카오모빌리티 자동차 예상 시간 | **ODsay 대중교통** 시간·경로 (없으면 거리로 추정). 1단계 허용 시간보다 길면 "○○분 넘음" |
| 한 달 실부담 | 월세 + 관리비 | **같음**: 월세 + 관리비. 관리비를 모르면 "–"로 두고 더하지 않음 |
| 보증금 | 보증금·월세 상한 초과를 따로 표시 | 1단계 모아둔 돈보다 크면 "○○만 원 부족" |
| 생활 시설 | 카카오 카테고리 검색, 반경·종류 미정 | 마트·병원·편의점 등 걸어서 몇 분 + 누르면 동네 지도 |
| 지원 | 없음 | **집마다 ✓·✗·△와 이유, 최대 금액, "지원 받으면 한 달 실부담"** (예: 신림 42만 → 22만, 월세 지원 20만 원 빼고) |
| 지도 | P1 | 회사와 세 집 위치, 출퇴근 경로를 한눈에 표시 |
| 추천 | 0–100 정규화 후 가중합 (기본 40/40/20) | 같은 가중합. 프리셋 또는 말로 정한 가중치. 지원 전 금액 기준. "이렇게 추천했어요" 이유와 "아쉬운 점" 표시 |

**종합 추천 계산 (v4 화면 숫자로 검산):** 균형 기준 비용 40%·시간 35%·생활 25%

| 집 | 한 달 실부담 | 출퇴근 | 비용 | 시간 | 생활 | 종합 |
|---|---:|---:|---:|---:|---:|---:|
| 신림 | 42만 | 30분 | 100 | 70 | 87.5 | 86.4 |
| 성수 | 60만 | 30분 | 73 | 70 | 90 | 76.2 |
| 역삼 | 90만 | 13분 (도보) | 28 | 100 | 87.5 | 68.1 |

- 비용 점수는 가장 싼 집을 100점으로 두고 실부담이 1만 원 많을 때마다 1.5점 깎은 값과 맞아요(성수 +18만 → 73, 역삼 +48만 → 28). 화면 숫자로 역산한 결과라 코드와 대조가 필요해요.
- 종합 점수는 지원 전 금액으로 계산해요. 지원 반영 실부담은 지원 표에만 나와요.
- 집마다 지원이 달라지는 예시: 27세면 세 집 모두 520만 원이지만, 역삼 집은 서울시 청년월세 조건을 넘어요(94.2만 원 > 93만 원). 35세가 되면 역삼만 40만 원으로 떨어져요.

### 3.5 AI와 데이터 원칙

| | v1.0 | v4 |
|---|---|---|
| 원칙 | 정책 판정·금액은 구조화 조건과 코드, AI는 조건 추출·추가 질문·근거 설명 | **돈·자격·점수는 코드가 계산**하고, AI는 **사람의 말을 숫자로 옮기거나 코드 결과를 근거로 설명**만 함 |
| 검증 장치 | 프로필 추출 결과의 스키마·범위 검증 (명세서 3절) | 코드 판정(나이, 월세 조건, 신청 마감, 범위 밖), 숫자 검사, 결론 검사, 출처 관리 |

v4에 새로 생긴 **"AI가 하는 일"** 표예요.

| # | 자리 | AI가 하는 일 | 코드가 하는 일 | 상태 |
|---|---|---|---|---|
| 1 | 공고문에 물어보기 (RAG) | 공고문 근거로만 답 작성, 근거 원문 표시 | 검색·필터, 나이·월세·마감 판정, 숫자·결론 검사 | 구현 |
| 2 | 1단계 대화 이해 | "회사 다녀요", "한시간 반"을 조건으로 정리 | 값 검증, 못 알아들으면 다시 묻기 | 구현 |
| 3 | 말한 우선순위 → 가중치 | "회사 가까운 게 제일 중요하고 돈은 좀 더 써도 돼요" → 비용 25 · 시간 55 · 생활 20 | 점수 계산. 가중치는 화면에 보여주고 사용자가 확인·조정 | 구현 예정 |
| 4 | 생활 점수 시설 고르기 | "밤에 늦게 와요", "운동 꾸준히 해요" → 편의점·헬스장 포함 | 시설까지 거리·도보 시간 계산 | 구현 예정 |
| 5 | 추천 이유 풀어 쓰기 | 코드 계산값으로 자연스럽게 설명 | 숫자 검사 (근거에 없는 숫자면 틀 문장으로) | 구현 예정 |
| 6 | 매물 정보 자동 입력 | 매물 글(OCR로 뽑은 글 또는 붙여넣은 글)에서 보증금·월세·관리비·면적·주소 정리 | OCR, 단위·범위 검사, 못 찾은 칸 비우기, 사용자 확인 | 구현 예정 |
| 7 | "왜 신림이야?" 후속 질문 | 계산된 비교 결과(실부담·출퇴근·생활·지원·점수 내역)를 넣어주면 그 값으로만 답 (검색 없음, RAG 아님) | 비교 결과 정리해서 넘기기, 숫자·결론 검사 | 구현 예정 |

### 3.7 LLM 모델

명세서 "구현 시작 전 확인할 항목"의 LLM 제공자 결정은 여전히 열려 있어요. 대신 v4에서 교체 방법이 정해졌어요.

- 개발·테스트는 OpenAI를 임시로 써요.
- `.env`의 `LLM_BASE_URL`, `LLM_MODEL`만 바꾸면 OpenAI 호환 API를 쓰는 다른 모델로 코드 수정 없이 교체해요.
- 바꾼 뒤에는 22문항 평가를 다시 돌려요.
- 돈·자격·마감 판정과 숫자·결론 검사는 모델과 상관없이 그대로 돌아가요.

### 3.8 기술 구조

v1.0은 Vue + Spring Boot + DB를 전제로 해요. v4의 현재 시연본은 다음 구조예요.

```
index.html (3단계 화면·판정 코드)
  → server.py (/api/ask, 127.0.0.1:5500)
  → rag.py (TF-IDF 검색 + 코드 판정)
  → LLM (근거로 답, 모델 교체 가능)
  → 숫자·결론 검사
```

API 키는 `.env`에만 두고 서버에서만 써요. 풀스택 팀 스택과 직접 겹치는 부분이라 **합치는 방법을 정해야 해요** (7절).

## 4. 새로 추가된 것

### 4.1 디지털 포용 강화안 (시각장애 청년, 본선 전 구현 예정)

| # | 기능 | 내용 | 난이도 |
|---|---|---|---|
| 1 | 듣기 버튼 | 1단계 질문, 2단계 결과, 공고문 답을 소리로 읽기 | 쉬움 |
| 2 | 큰 글씨·고대비 | 기존 "쉬운 화면"을 확장 (시각·저시력) | 쉬움 |
| 3 | 말로 답하기 | 1단계 질문에 음성으로 답하면 글자로 입력 | 보통 |

### 4.2 음성 모드

- 화면을 보지 않고 1~3단계를 말로 진행해요. 스크린리더와 겹치지 않게 자동 재생하지 않고 버튼으로 시작해요.
- 3단계 비교는 "결론 먼저 → 항목별 순위 → 차이 → 더 들을지 선택" 순서로 말해요. "돈", "성수랑 신림 비교", "역삼 자세히", "왜 신림이야?", "다시"로 이어가요.
- 음성 문장은 계산된 숫자로 **코드가 틀에 맞춰** 만들어요. 화면과 음성의 숫자가 항상 같아요.
- 기술: 크롬 Web Speech API(무료, 서버 불필요). 필요하면 클라우드 TTS·STT, 오프라인용 Whisper·MeloTTS로 확장해요.

### 4.3 그 밖의 추가

- **매물 정보 자동 입력:** 직방·다방 매물 캡처를 올리면 OCR로 글자를 뽑고, LLM이 보증금·월세·관리비·면적·주소를 정리해 입력칸을 채워요. 매물 글을 복사해 붙여넣으면 OCR 없이 바로 정리해요. 코드가 단위·범위를 검사하고 못 찾은 칸은 비워두며(지어내지 않음), 사용자가 확인해야 비교에 들어가요. 매물을 우리가 가져올 수 없는 문제를 사용자가 가져오는 방식으로 풀어요(크롤링 아님). OCR은 표 배치를 잃어 항목과 숫자가 잘못 짝지어질 수 있어서 확인 단계가 꼭 필요해요.
- **교통비 참고 표시 (추가 사항):** 출퇴근 칸에 한 달 예상 교통비(ODsay 편도 요금 × 2 × 20일)를 참고로만 보여줘요. 한 달 실부담과 비용 점수에는 넣지 않아요. 출퇴근이 먼 집이 시간 점수에서 이미 깎이니까 비용에서 또 깎이지 않게 하고, 정기권·재택처럼 사람마다 차이가 큰 추정값이 비용 비교를 흔들지 않게 하려는 거예요.
- **범위 밖 질문 처리:** 만 19~39세 밖이면 상담기관으로 바로 안내
- **로그인 화면:** 카카오·네이버 간편 로그인 화면으로 이름 표시 (시연은 이름 입력)
- **할 일 안내:** 신청 시기와 함께 전입신고, 세대 분리 안내
- **마무리 연결:** 집 보러 갈 때 서울시 안심계약 도움서비스 동행 안내
- **시연 시나리오 8단계:** 1단계 대화 → 지원 추천 → 공고문 질문 → 집 비교 → 조건 바꾸기 → 범위 밖 질문 → **우선순위 말하기** → 음성 모드
- **다음 단계:** 음성 모드·접근성 점검(axe-core), 장애인 청년 주거 지원 데이터, 서울시 전월세 실거래로 "예산에 맞는 동네" 추천, 실제 로그인·공고 알림, **AI 추천 보조**, **LLM 최종 선정 후 평가 재실행**

## 5. 그대로인 것

- 서비스명 첫집 내비, 대상(서울 만 19~39세 청년 1인 가구), 서울 한정 범위
- 판정·금액·점수는 코드가 계산
- 정책마다 근거 문장과 공고 링크 표시, 자료에 없으면 추가 확인 필요
- 후보 집 2~3곳 직접 입력, 시연 후보 성수·역삼·신림, 목적지 멀티캠퍼스 역삼
- 시연 페르소나 정연(만 27세, 월 230만 원)
- **한 달 실부담 = 월세 + 관리비** (PRD 4절, 명세서 5절 제안과 같음)
- **종합 추천 = 0–100점 지표의 가중합** (명세서 5절 산식과 같음)
- 카카오 주소·장소 검색으로 주소와 주변 시설 조회
- 일부 조회가 실패해도 나머지 결과 유지
- 서비스 LLM 미정

## 7. 팀에서 정해야 할 것

1. **서버 구조.** 시연본은 Python(server.py, rag.py), 풀스택 계획은 Spring Boot예요.
   - RAG·AI는 Python 서비스로 두고 Spring Boot가 호출
   - 전부 Spring Boot로 옮김
   - 시연은 현재 구조로 가고 풀스택은 화면·데이터 저장만 담당
2. **추천 점수 세부값.** 균형(40/35/25) 외 프리셋 3개의 가중치, 비용·시간 점수 감점 폭, AI가 낸 가중치의 허용 범위(합계 100, 각 0~100, 생활이 양수면 시설 1종 이상)
3. **지원 반영 실부담 계산법.** 지금은 월 지원액(월세 지원 20만 원)만 빼요. 이사비 같은 1회성 지원과 기간이 다른 지원을 어떻게 다룰지, 종합 점수에도 반영할지
4. **(추가 사항) 교통비 참고 표시.** 넣을지, 넣는다면 요금 × 2 × 20일 고정인지 1단계 상황(학생·직장인)에 따라 일수를 바꿀지
5. **서비스 LLM 제공자·모델.** 아직 미정. 정하면 22문항 평가 재실행
6. **DB 범위.** 본선까지 5일이라 정책 버전 관리(DRAFT/PUBLISHED), revision 충돌 처리 같은 운영 수준 설계는 시연 이후로 미루고, 검증된 정책을 읽기 전용 시드로 넣는 방식이 현실적이에요.
7. **담당.** AI 보조 5개 자리(우선순위·시설·추천 이유·후속 질문·매물 자동 입력)와 디지털 포용 강화안을 누가 맡을지
